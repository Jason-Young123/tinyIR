# LLVM 入门：从源代码到机器码

本文根据 `D01-S02-CompilerIntroduction.pdf` 第 15 页的 **LLVM Overview** 整理，并补充适合初学者理解的背景、例子和术语解释。

第 15 页想表达的主线可以概括为：

```text
不同源语言
    |
    v
前端（Front-end）
    |
    v
未优化的 LLVM IR
    |
    v
LLVM 中端（Middle-end）
    |
    v
优化后的 LLVM IR
    |
    v
后端（Back-end）
    |
    v
某种硬件的汇编代码或机器码
```

最重要的一句话是：

> LLVM 是一套可复用的编译器基础设施。它用统一的 LLVM IR 连接各种源语言和各种硬件，再通过中间的优化与代码生成组件完成编译。

## 1. LLVM 到底是什么

### 1.1 LLVM 不是一种编程语言

LLVM 不是像 C、C++、Rust、Python 那样让程序员直接编写业务代码的编程语言。

它也不是一种具体的处理器，更不是某个单独的编译器命令。

LLVM 更准确的定位是：

- 一套编译器框架；
- 一组可组合的编译器库和工具；
- 一个围绕中间表示 LLVM IR 构建的编译器基础设施；
- 一套可以支持多种源语言和多种目标硬件的代码生成体系。

因此，LLVM 更像“搭建编译器的工具箱”，而不是一把只负责编译 C 语言的固定工具。

### 1.2 LLVM 名称的由来

LLVM 最初常被解释为 **Low Level Virtual Machine**，中文通常译为“低级虚拟机”。

不过，随着项目发展，LLVM 已经不再只是一个虚拟机，也不再局限于一个具体的“低级虚拟机”概念。因此今天通常直接把 **LLVM** 当作项目名称使用，而不强调它的完整英文展开。

这也解释了一个常见误区：

> LLVM 不是 Java Virtual Machine，也不是一个运行时虚拟机。LLVM 的核心任务是帮助编译器把程序转换成高效的目标代码。

### 1.3 LLVM 的历史背景

第 15 页提到，LLVM 最初由 Chris Lattner 在美国伊利诺伊大学攻读硕士期间开发，后来逐渐发展成广泛使用的开源编译器项目。

LLVM 的影响力来自一个很实用的设计：

1. 不同语言的前端各自处理自己的语法和语义；
2. 它们把代码转换成统一的 LLVM IR；
3. 统一的中端优化器可以复用；
4. 不同硬件的后端负责生成各自的机器代码。

这样，语言开发者和硬件开发者不必为每一种语言和每一种处理器重新实现全部编译流程。

## 2. 为什么需要 LLVM

假设有 3 种源语言和 3 种处理器：

- 源语言：C、Rust、Fortran；
- 目标硬件：x86、ARM、RISC-V。

如果每种语言都直接生成每种硬件的机器码，那么大致需要维护：

```text
C      -> x86
C      -> ARM
C      -> RISC-V
Rust   -> x86
Rust   -> ARM
Rust   -> RISC-V
Fortran-> x86
Fortran-> ARM
Fortran-> RISC-V
```

语言数量和硬件数量增加时，组合数量会迅速膨胀。

LLVM 把问题拆开：

```text
C       -> LLVM IR
Rust    -> LLVM IR
Fortran -> LLVM IR

LLVM IR -> x86
LLVM IR -> ARM
LLVM IR -> RISC-V
```

于是**前端主要解决“如何理解一种语言”，后端主要解决“如何生成一种硬件代码”，两者通过 LLVM IR 解耦。**

这就是 LLVM 最核心的工程价值之一：**复用和解耦**。

## 3. 编译器的基本三段式流程

第 15 页把 LLVM 编译流程分成前端、LLVM 中端和后端。理解这三部分，是理解 LLVM 的入口。

## 3.1 前端：理解源语言

前端负责把程序员写的源代码变成编译器内部可以处理的表示。

以这段 C 代码为例：

```c
int add(int a, int b) {
    return a + b;
}
```

前端通常需要完成以下工作：

1. **词法分析**
   - 把字符组成的源代码切分成关键字、标识符、数字、运算符等。
   - 例如识别出 `int`、`add`、`a`、`+`、`b`。

2. **语法分析**
   - 检查这些单词是否符合 C 语言的语法。
   - 例如函数是否有正确的括号和花括号。

3. **语义分析**
   - 检查代码的含义是否合法。
   - 例如变量是否声明过、函数参数类型是否匹配、返回值是否符合函数返回类型。

4. **构造前端内部表示**
   - 很多编译器会先构造 AST，即抽象语法树。
   - AST 保留了较多源语言结构，例如函数、表达式、语句和类型。

5. **生成 LLVM IR**
   - 将语言相关的表示转换成相对统一的低级中间表示。

常见的 LLVM 前端包括：

- **Clang**：C、C++、Objective-C 等语言的前端；
- **rustc**：Rust 编译器，其中一部分代码生成流程可以使用 LLVM；
- **Flang**：Fortran 前端；
- Swift、Julia、Mojo 等语言也可以使用 LLVM 相关基础设施；
- Numba 可以把部分 Python 数值代码编译到 LLVM。

需要区分两个概念：

> Clang 是 C/C++ 前端；LLVM 是它使用的编译器基础设施。Clang 和 LLVM 不是同一个东西，但 Clang 通常会把 LLVM 作为后续优化和代码生成平台。

## 3.2 LLVM IR：前端和后端之间的共同语言

### LLVM IR 是什么

IR 是 **Intermediate Representation** 的缩写，意思是“中间表示”或“中间代码”。

LLVM IR 是 LLVM 体系中的核心数据结构。它处在源代码和机器码之间：

```text
C/C++/Rust 等源代码
        |
        v
      LLVM IR
        |
        v
x86/ARM/RISC-V 等机器代码
```

第 15 页将 LLVM IR 描述为一种接近机器指令层次的抽象低级 IR。它比 C、C++ 这样的高级语言低级很多，但又没有绑定到某一种具体处理器。

### LLVM IR 的几个特点

#### 统一

不同源语言可以把许多基本操作表达成统一形式。例如整数加法、函数调用、内存访问和条件跳转，都可以使用 LLVM IR 表示。

#### 相对独立于硬件

同一份 LLVM IR 不直接等同于 x86 汇编，也不直接等同于 ARM 汇编。

它描述的是“程序要做什么”，后端再结合目标硬件决定“如何用该硬件实现”。

#### 静态类型

LLVM IR 中的值通常带有明确类型，例如：

```text
i1      1 位整数，常用于布尔条件
i32     32 位整数
i64     64 位整数
float   单精度浮点数
double  双精度浮点数
```

明确的类型信息有助于编译器发现错误并进行优化。

#### 使用虚拟寄存器

LLVM IR 中常见 `%a`、`%sum` 这样的名字。它们不是最终硬件上的真实寄存器，而是“虚拟寄存器”或 SSA 值。

后端会在生成目标代码时，把这些虚拟值分配到真实寄存器或内存中。

#### 通常采用 SSA 形式

SSA 是 **Static Single Assignment** 的缩写，即“静态单赋值”。

SSA 的基本规则是：

> 每个 SSA 值只定义一次。

例如，下面的普通伪代码允许多次修改 `x`：

```text
x = 1
x = x + 2
x = x * 3
```

在 SSA 中通常会写成：

```text
x1 = 1
x2 = x1 + 2
x3 = x2 * 3
```

这样每个值只有一个定义，数据依赖关系更加明确，常量传播、死代码删除等优化也更容易实现。

### 一个简单的 LLVM IR 示例

源代码：

```c
int add(int a, int b) {
    return a + b;
}
```

对应的 LLVM IR 可以近似写成：

```llvm
define i32 @add(i32 %a, i32 %b) {
entry:
  %sum = add i32 %a, %b
  ret i32 %sum
}
```

逐项解释：

- `define`：定义一个函数；
- `i32`：函数返回一个 32 位整数；
- `@add`：函数名称使用 `@` 开头；
- `%a` 和 `%b`：函数参数，是 LLVM IR 中的 SSA 值；
- `%sum`：`add` 指令产生的新 SSA 值；
- `add i32 %a, %b`：对两个 32 位整数做加法；
- `ret i32 %sum`：返回 `%sum`。

这里的 `%sum` 不是某个固定的 x86 寄存器名字。它只是 LLVM IR 中的一个临时值名称。

### LLVM IR 的三种常见形态

LLVM IR 常见有三种相关形态：

- **文本 LLVM IR**：通常是 `.ll` 文件，便于阅读和调试；
- **LLVM bitcode**：通常是 `.bc` 文件，使用二进制形式保存；
- **内存中的 LLVM IR 对象**：编译器程序通过 LLVM API 直接构造和修改。

例如可以用 Clang 生成文本 LLVM IR：

```bash
clang -S -emit-llvm add.c -o add.ll
```

具体命令选项可能随 LLVM 版本和平台略有差异，但思想不变：让前端输出尚未生成机器码的 LLVM IR。

## 3.3 中端：在 LLVM IR 上做通用优化

中端也叫 **middle-end**。它位于前端和后端之间，主要处理与具体源语言和具体硬件相对独立的优化。

第 15 页把 LLVM 中端称为“The Optimizer”，即优化器。

### 为什么要在 IR 上优化

直接对每种源语言做优化会造成重复实现，直接对每种机器码做优化又过于复杂。

LLVM IR 提供了一个统一层：

```text
C 前端       \
Rust 前端     \
Fortran 前端  ---> 统一的 LLVM IR ---> 通用优化
```

只要不同前端生成的 LLVM IR 遵守约定，许多优化就可以复用。

### 常见的中端优化

#### 常量折叠

源代码：

```c
int f() {
    return 2 * 3 + 1;
}
```

编译器可以在编译期间直接计算结果：

```c
int f() {
    return 7;
}
```

程序运行时就不需要再做乘法和加法。

#### 死代码删除

```c
int f(int x) {
    int unused = x * 10;
    return x + 1;
}
```

如果 `unused` 的值从未被使用，编译器可以删除相关计算。

#### 函数内联

```c
int inc(int x) {
    return x + 1;
}

int f(int x) {
    return inc(x);
}
```

编译器可能把 `inc(x)` 的函数体直接放到调用处，减少函数调用开销，并为后续优化创造机会。

#### 公共子表达式消除

```c
int f(int a, int b) {
    int x = a + b;
    int y = a + b;
    return x * y;
}
```

`a + b` 可以只计算一次，再复用这个结果。

#### 循环优化

编译器可能进行循环不变代码外提、循环展开、循环合并、循环向量化等优化。

例如：

```c
for (int i = 0; i < n; i++) {
    a[i] = b[i] + 1;
}
```

在适合的目标机器上，编译器可能把一次处理一个元素的循环改造成 SIMD 向量指令，一次处理多个元素。

需要注意：

> LLVM 不会无条件地执行所有优化。优化必须遵守源程序语义，还要考虑别名关系、溢出规则、浮点精度、目标硬件特性和编译选项。

### 未优化 IR 和优化 IR

第 15 页特别区分了：

- **Unoptimized LLVM IR**：前端刚生成的、尚未经过主要优化的 LLVM IR；
- **Optimized LLVM IR**：中端优化器处理后的 LLVM IR。

未优化 IR 往往更接近源程序结构，便于调试和定位前端问题，但可能包含很多冗余的内存操作和临时值。

优化后的 IR 通常更简洁，也更适合后端生成高效机器码，但**它可能已经和源代码结构有较大差异**。

## 3.4 后端：针对目标硬件生成机器代码

后端也叫 **back-end**。它把优化后的 LLVM IR 转换成特定目标架构的汇编代码、目标文件或机器码。

第 15 页列出的目标架构包括：

- x86，常见于 Intel 和 AMD 处理器；
- ARM，常见于手机、嵌入式设备和 Apple 芯片；
- RISC-V；
- 其他目标架构。

### 后端主要做什么

#### 指令选择

LLVM IR 的一条操作可能对应目标架构的一条或多条指令。

例如 LLVM IR 中的整数加法，在不同处理器上会被选择成不同的机器指令。

#### 寄存器分配

LLVM IR 中可以有很多虚拟寄存器，但真实处理器的寄存器数量有限。

后端需要决定：

- 哪些值放在哪些真实寄存器中；
- 哪些值暂时放入栈或内存；
- 什么时候把值从内存加载回寄存器。

#### 指令调度

处理器中的指令可能存在延迟和资源竞争。后端可以调整部分指令顺序，在不改变语义的前提下提高流水线利用率。

#### 目标相关优化

不同处理器有不同的特性，例如：

- 可用的寄存器数量不同；
- SIMD 指令集不同；
- 指令延迟和吞吐量不同；
- 内存访问约束不同；
- 调用约定不同。

后端需要针对这些差异生成代码。

#### 生成汇编或目标文件

最终结果可以是：

- 汇编文件，例如 `.s`；
- 目标文件，例如 `.o` 或 `.obj`；
- 进一步链接后形成可执行文件或库。

链接器通常是完整工具链中的另一个组件，但它接收的目标文件往往已经由 LLVM 后端生成。

## 4. 用一个完整例子理解 LLVM 流程

下面用一段简单的 C 代码贯穿整个过程：

```c
int transform(int x) {
    int y = x * 2;
    return y + 1;
}
```

### 4.1 源语言层

程序员看到的是：

```text
先把 x 乘以 2，得到 y；
再把 y 加 1 并返回。
```

这个层次包含变量名、赋值语句和源语言语法。

### 4.2 前端处理

C 前端会检查：

- `transform` 是否是合法函数定义；
- `x` 是否是已经声明的参数；
- `x * 2` 的类型是否正确；
- 返回值是否符合 `int` 类型。

检查通过后，Clang 会把它转换为 LLVM IR。

### 4.3 未优化 LLVM IR

一种简化后的 IR 可以表示为：

```llvm
define i32 @transform(i32 %x) {
entry:
  %y = mul i32 %x, 2
  %result = add i32 %y, 1
  ret i32 %result
}
```

此时 LLVM IR 已经不再需要理解 C 语言中的“局部变量声明”或“赋值语句”概念，而是直接表示整数乘法、整数加法和返回。

### 4.4 中端优化

中端看到：

```text
y = x * 2
result = y + 1
```

它可能发现这相当于：

```text
result = x * 2 + 1
```

在某些目标架构上，后端可以进一步把它选择为一条适合的地址计算类指令。例如某些 x86 编译结果可能类似：

```asm
leal 1(%rdi,%rdi), %eax
retq
```

这条汇编指令利用地址计算形式完成 `2 * x + 1`。实际输出会受到 LLVM 版本、编译选项、目标 CPU、调用约定和寄存器分配影响，因此这里的汇编只用于说明思路，不应看作唯一结果。

### 4.5 后端生成目标代码

如果目标是 x86，LLVM 后端会生成 x86 汇编；如果目标是 ARM，则生成 ARM 汇编；如果目标是 RISC-V，则生成 RISC-V 汇编。

同一份高层语义：

```text
return 2 * x + 1;
```

会因为目标架构不同而有不同的机器指令，但程序行为应保持一致。

## 5. 条件分支如何经过 LLVM

为了联系控制流图和 SSA，可以看下面的代码：

```c
int max0(int x) {
    if (x > 0)
        return x;
    else
        return 0;
}
```

LLVM IR 可能近似表示为：

```llvm
define i32 @max0(i32 %x) {
entry:
  %cond = icmp sgt i32 %x, 0
  br i1 %cond, label %positive, label %zero

positive:
  br label %merge

zero:
  br label %merge

merge:
  %result = phi i32 [ %x, %positive ], [ 0, %zero ]
  ret i32 %result
}
```

这里有几个重要概念：

- `icmp sgt`：比较两个有符号整数是否满足“大于”；
- `br`：根据条件跳转到不同基本块；
- `positive` 和 `zero`：两条控制流路径；
- `merge`：两条路径重新汇合的基本块；
- `phi`：根据控制流从哪条路径到达，选择对应的值。

在普通 C 代码里，变量可以在不同分支中被赋值；**在 LLVM 的 SSA 形式中，每个值仍然只能定义一次**，所以需要 `phi` 节点表示“从不同路径带来的值”。

这也是 LLVM IR 看起来像汇编、但又不是传统汇编的原因之一：它显式记录了控制流和数据流关系，方便优化器分析。

## 6. LLVM 的核心特点

### 6.1 源语言和目标硬件解耦

**前端负责语言，后端负责硬件，中端在统一 IR 上复用。**

这使得：

- **增加一种源语言时，主要开发新的前端；**
- **增加一种硬件时，主要开发新的后端；**
- **通用优化不必为每种语言重复实现。**

### 6.2 LLVM IR 是共同接口

LLVM IR 是不同编译器组件之间的接口。

前端把程序交给中端，中端把优化后的 IR 交给后端。只要接口契约保持一致，各部分就可以独立开发和替换。

### 6.3 优化器由许多 Pass 组成

LLVM 的优化不是一个神秘的黑盒，而是由许多相对独立的 **pass** 组成。

**一个 pass 通常完成一类工作**，例如：

- 删除死代码；
- 简化控制流；
- 传播常量；
- 做函数内联；
- 优化循环；
- 进行向量化。

多个 pass 可以按一定顺序组成优化流水线。**顺序很重要，因为前一个 pass 产生的机会可能会被后一个 pass 利用**。

### 6.4 支持多种目标架构

LLVM 后端支持许多处理器和平台。编译器可以通过目标三元组、CPU 类型和特性参数来选择目标。

例如同一个程序可以分别编译为：

```text
x86-64 Linux
ARM64 macOS
RISC-V Linux
```

### 6.5 既适合编译器，也适合语言工具链

LLVM 不只用于把 C/C++ 编译成可执行文件，还可以用于：

- 新编程语言；
- 领域专用语言；
- JIT，即运行时即时编译；
- 静态分析工具；
- 代码格式和检查工具；
- GPU、AI 和加速器编译器。

### 6.6 低级但保留足够的语义信息

LLVM IR 已经接近机器级，因此适合做底层优化和代码生成；同时它仍保留类型、函数、基本块、调用关系等结构信息。

如果一开始就把程序完全变成机器码，许多高层优化会变得很困难。LLVM IR 在可分析性和接近硬件之间取得了平衡。

## 7. LLVM 与传统“编译器”的关系

初学者容易把“LLVM”和“编译器”完全画等号。更准确的关系是：

```text
编译器
├── 前端
├── 中间表示
├── 中端优化器
├── 后端代码生成器
└── 汇编器、链接器等工具
```

LLVM 项目提供了其中大量通用组件，尤其包括：

- LLVM IR；
- IR 的解析、验证和变换工具；
- 通用优化器；
- 多目标后端；
- 汇编器和相关目标文件处理能力；
- JIT 和调试支持等。

一个完整的语言编译器可以使用 LLVM，也可以只使用 LLVM 的某一部分。

例如：

- Clang 使用 LLVM 作为 C/C++ 的后续编译平台；
- Rust 编译器可以使用 LLVM 后端生成机器代码；
- 某个领域专用编译器可能只借用 LLVM 的 IR 和后端；
- 另一个编译器也可以在 LLVM 之前增加自己的高级 IR。

## 8. LLVM 与 MLIR 的关系

PDF 后续第 16 页开始介绍 MLIR。理解两者的关系很重要。

### 8.1 LLVM IR 更偏低层

LLVM IR 适合表示：

- 基本算术；
- 加载和存储；
- 函数调用；
- 分支和基本块；
- 指针和底层数据布局；
- 接近机器指令的计算。

但是，LLVM IR 并不擅长直接表达“这是一个高层矩阵乘法”“这是一个张量转置”“这是一个 GPU 线程块”。

### 8.2 MLIR 可以保留高层结构

例如 AI 程序中的矩阵乘法，可以先在更高层的 MLIR dialect 中表示：

```text
linalg.matmul
```

经过多次 lowering 后，它可以依次变成：

```text
矩阵乘法
    -> 分块后的矩阵乘法
    -> 多层循环
    -> 内存访问和标量运算
    -> LLVM IR
    -> x86/ARM/GPU 等目标代码
```

因此可以粗略理解为：

> MLIR 更适合承载多个抽象层级和领域专用语义；LLVM IR 更接近底层代码生成。MLIR 常常把程序逐步降低到 LLVM 相关表示，再利用 LLVM 的成熟后端生成机器码。

这不是说 LLVM 只能做低级工作，**而是说 LLVM IR 的设计中心更接近底层代码生成；MLIR 则专门强调多层级和可扩展的中间表示。**

## 9. 一个最小的实践流程

可以使用下面的 C 文件进行观察。

```c
// demo.c
int transform(int x) {
    int y = x * 2;
    return y + 1;
}
```

生成文本 LLVM IR：

```bash
clang -S -emit-llvm demo.c -o demo.ll
```

查看优化前后的差异，可以尝试不同优化级别：

```bash
clang -S -emit-llvm -O0 demo.c -o demo-O0.ll
clang -S -emit-llvm -O2 demo.c -o demo-O2.ll
```

生成目标架构的汇编代码：

```bash
clang -S -O2 demo.c -o demo.s
```

这些命令背后的逻辑是：

```text
demo.c
  |
  | Clang 前端
  v
demo.ll
  |
  | LLVM 中端优化
  v
优化后的 LLVM IR
  |
  | LLVM 后端
  v
demo.s
```

不同版本的 Clang 可能会生成不同格式的 IR 或汇编，但应当始终围绕同一条流水线工作。

## 10. 初学者最容易混淆的几个问题

### LLVM 是不是一个编译器命令

不完全是。`clang` 是一个常用的编译器驱动程序，`llc`、`opt`、`llvm-as`、`llvm-dis` 等是 LLVM 项目中的不同工具。LLVM 本身是由这些工具、库、IR 和后端组成的项目体系。

### LLVM IR 是不是汇编

LLVM IR 和汇编都属于低级表示，也都包含指令和控制流，但 LLVM IR 仍然是虚拟的、与目标硬件相对独立的表示。

LLVM IR 中的虚拟寄存器、类型和指令，需要经过目标后端处理后，才能变成真实处理器能执行的机器指令。

### LLVM 能不能把任何程序都优化得更快

不能。优化必须保持程序语义，而且受以下因素影响：

- 源代码是否允许变换；
- 编译器是否能证明变换安全；
- 数据是否可能别名；
- 目标硬件是否支持某种指令；
- 优化是否会增加代码体积；
- 浮点计算是否允许改变精度或顺序。

### LLVM IR 是否只有一种写法

LLVM IR 有明确的语法和语义规则，但同一个源程序可能有多种等价的 IR 表示。不同前端、LLVM 版本和优化级别都可能影响具体结果。

### 为什么不直接从 C 生成机器码

当然可以直接生成，但这样会让前端承担大量硬件相关工作，也很难复用通用优化。

LLVM 的 IR 提供了一个中间层，让：

- 前端更专注于语言；
- 优化器更专注于程序变换；
- 后端更专注于目标硬件。

## 11. 如何建立对 LLVM 的整体心智模型

可以把 LLVM 想成一条生产线：

```text
前端：读懂一种语言
      |
      v
LLVM IR：统一的中间产品
      |
      v
中端：对产品做通用加工和优化
      |
      v
后端：按照目标硬件的规格加工
      |
      v
汇编代码/目标文件/机器码
```

也可以把它理解成一个“翻译中转站”：

- C、Rust、Fortran 等是不同的人类语言；
- LLVM IR 是一种编译器共同语言；
- x86、ARM、RISC-V 是不同的硬件语言；
- 前端负责翻译到共同语言；
- 后端负责从共同语言翻译到硬件语言；
- 中端在共同语言上做不依赖具体源语言的优化。

## 12. 对第 15 页的最终总结

第 15 页的每一条信息都可以归结为以下几点：

1. **LLVM 是编译器框架，而不是一种编程语言。**
2. **LLVM IR 是连接前端、中端和后端的核心中间表示。**
3. **前端把多种源语言转换成 LLVM IR。**
4. **LLVM 中端在 LLVM IR 上执行通用优化，产生优化后的 LLVM IR。**
5. **后端把优化后的 LLVM IR 转换成 x86、ARM、RISC-V 等架构的汇编代码或机器码。**
6. **LLVM 的主要价值是复用、解耦、可扩展和多目标支持。**
7. **MLIR 可以在 LLVM 之前保留更高层、更领域化的表示，最后再逐步降低到 LLVM 相关表示。**

如果只记住一张图，请记住：

```text
源语言
  -> 前端
  -> 未优化 LLVM IR
  -> LLVM 中端优化
  -> 优化后的 LLVM IR
  -> 目标后端
  -> 汇编代码/机器码
```
