## 1. 为什么需要 ODS

### 1.1 定义一个 Operation 不只是写一行名字

在 MLIR 中，一个 Operation 可能看起来很简单。例如：

```mlir
%res = arith.addi %lhs, %rhs : i32
```

但要让这个 Operation 真正可用，通常还需要为它提供多类接口：

```text
对象接口（Object API）
  getters、setters、builders、verifier

汇编格式接口（Format API）
  parser、printer、serializer、deserializer

语义接口（Semantic API）
  folder、rewrite pattern、interface registration、
  trait registration 等
```

也就是说，定义一个 Operation 往往需要同时处理：

- 它属于哪个 dialect；
- 它叫什么；
- 有哪些 operands 和 results；
- 每个 operand/result 的类型是什么；
- 如何检查输入是否合法；
- 如何从文本解析它；
- 如何把它打印回文本；
- 如何构造它；
- 是否支持常量折叠、重写或某些 interface；
- 是否具有 Region、terminator 或 parent 约束。

课件用一个直观的数量级说明这个问题：如果完全手写，一个新 Operation 可能需要大约 500 行 C++ 样板代码。这里的 500 行是课件中的近似示意，不是所有 Operation 都固定需要这个行数。

### 1.2 ODS 的基本想法

ODS 提供一种声明式写法，让开发者描述“这个 Operation 是什么”，而不是手工实现所有重复的 C++ 胶水代码。

典型流程是：

```text
在 .td 文件中声明 Operation
        |
        v
TableGen 读取这些声明
        |
        v
生成 Operation 的 C++ 声明、访问器和部分实现
        |
        v
开发者只为特殊语义补充必要的 C++ 代码
```

下面是课件中 `arith.addi` 的简化定义：

```tablegen
def Arith_AddIOp : Op<Arith_Dialect, "addi", [...]> {
  let arguments = (ins SignlessIntegerLike:$lhs,
                       SignlessIntegerLike:$rhs);
  let results    = (outs SignlessIntegerLike:$result);
  let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
}
```

这段声明描述了：

- Operation 属于 `Arith_Dialect`；
- 在 MLIR 文本中使用的 mnemonic 是 `addi`；
- 有两个输入：`$lhs` 和 `$rhs`；
- 有一个结果：`$result`；
- 输入和结果需要满足 `SignlessIntegerLike` 约束；
- 文本语法大致是：

  ```mlir
  %res = arith.addi %lhs, %rhs : i32
  ```

ODS 生成的代码不是“魔法运行时”，而是编译期生成的普通 C++ 代码。开发者仍然需要理解 Operation 的结构和约束，只是不必反复手写相同的基础代码。

## 2. TableGen 基础

ODS 建立在 LLVM TableGen DSL 之上。理解 TableGen 的两个核心概念，就能读懂大部分简单的 ODS 定义：

```text
class = 可复用的描述模板
def   = 基于模板创建的具体定义
```

### 2.1 `class`：定义可复用的字段和规则

```tablegen
class ExampleClass<int parameter> {
  int field_ = !add(parameter, 1);
  string otherField = ?;
}
```

这里的 `class` 类似 C++ 中的类或模板：

- `parameter` 是一个整数参数；
- `field_` 是一个整数型字段；
- `!add(parameter, 1)` 是 TableGen 的表达式，表示把参数加 1；
- `otherField` 是字符串字段；
- `?` 表示这个字段暂时没有默认的具体值。

TableGen 的 `class` 主要用于复用字段和定义。ODS 中的 `Op` 就是一个重要的基类模板。

### 2.2 `def`：创建一个具体定义

```tablegen
def ExampleDef : ExampleClass<5> {
  let otherField = "a value";
}
```

这个 `def` 使用 `ExampleClass<5>` 作为基类，并通过 `let` 设置字段：

```text
field_      = !add(5, 1) = 6
otherField  = "a value"
```

对 ODS 来说，生成器主要查找具体的 `def`，然后为每个 `def` 生成相应的代码。可以这样理解：

```text
class = 规定“哪些字段可以描述一个 Operation”
def   = 给某个具体 Operation 填写这些字段
let   = 修改或补充继承来的字段值
```

课件特别强调：TableGen 的 `class` 主要是代码生成阶段的复用机制。它不是运行时的 C++ 类，也不会直接表示一个运行中的 MLIR Operation。

### 2.3 常见 TableGen 类型

课件列出了 ODS 中常见的 TableGen 类型：

| TableGen 类型 | 字面量示例 | 直观理解 |
|---|---|---|
| `int` | `0`、`-5`、`0x5` | 整数，生成时通常对应 `int64_t` |
| `string` / `code` | `"text"`、`[{ raw code }]` | 字符串或多行代码片段 |
| `bit` | `0`、`1`、`true`、`false` | 布尔开关 |
| `dag` | `(op Value:$name...)` | 带有操作符和命名元素的描述结构 |
| `list<type>` | `[ ... ]` | 某种类型的列表 |
| `ClassName` | `ClassName<...>` | 某个 TableGen 类的实例 |

在 ODS 中，`arguments`、`results` 和 `regions` 经常使用 `dag` 表达，因为它们需要同时记录元素的类别、顺序和名字。例如：

```tablegen
let arguments = (ins I32:$lower, I32:$upper);
let results = (outs List_ListType:$result);
```

其中：

- `ins` 表示输入 operands；
- `outs` 表示输出 results；
- `I32:$lower` 表示一个类型约束为 `I32`、名字为 `$lower` 的输入；
- `List_ListType:$result` 表示一个类型约束为 `List_ListType`、名字为 `$result` 的结果。

## 3. 从一个简单的 Operation 开始

课件使用一个 `list` dialect 作为贯穿示例。先看最简单的 `list.empty`：

```tablegen
def List_EmptyOp : Op<List_Dialect, "empty"> {
  // 没有输入，也没有结果
}
```

这段定义的含义是：

- `List_EmptyOp` 是 TableGen 中的定义名；
- `Op<...>` 是所有 Operation 的基础描述；
- `List_Dialect` 指定所属 dialect；
- `"empty"` 是 Operation 的 mnemonic；
- 因为没有指定 operands 和 results，所以默认都是 0 个。

### 3.1 Operation 命名规则

课件中的命名约定是：

```text
ODS 定义名：List_EmptyOp
                         |
                         +-- 第一个下划线之前的前缀通常用于标识 dialect

生成的 C++ 类：mlir::list::EmptyOp
文本 mnemonic：list.empty
```

常见约定可以概括为：

| 项目 | 示例 | 作用 |
|---|---|---|
| TableGen 定义名 | `List_EmptyOp` | 通常使用 PascalCase，并以 dialect 前缀开头 |
| C++ Operation 类 | `EmptyOp` | 生成到 `mlir::list` 命名空间 |
| Operation mnemonic | `list.empty` | 文本 IR 中使用的名字，通常是 snake_case |

`List_EmptyOp` 中的 `List_` 前缀帮助 TableGen 和人类读者识别归属；生成的 C++ 类名通常去掉第一个下划线之前的前缀，得到 `EmptyOp`。

### 3.2 声明 operands 和 results

例如，一个 `list.range` 可以接收上下界并返回一个 list：

```tablegen
def List_RangeOp : List_Op<"range"> {
  let arguments = (ins I32:$lower, I32:$upper);
  let results = (outs List_ListType:$result);
}
```

它表达的 Operation 结构是：

```text
operands:
  $lower : i32
  $upper : i32

results:
  $result : !list.list<...>
```

这里的 `List_Op` 通常是该 dialect 自己定义的辅助基类，用来统一设置 dialect、命名空间或公共 traits。课件重点不在这个辅助类的实现，而在于如何为具体 Operation 覆盖 `Op` 的字段。

### 3.3 `arguments` 和 `results` 的默认值

`Op` 基类中相关字段的默认形式可以理解为：

```tablegen
dag arguments = (ins);
dag results = (outs);
```

因此，只有在 Operation 有输入或输出时，才需要显式填写对应字段。

## 4. 类型约束：告诉生成器什么类型是合法的

ODS 中的类型约束（TypeConstraint）用于描述 operands 或 results 允许使用哪些类型。它们不仅用于生成 C++ 类型访问器，也会参与解析和验证。

### 4.1 常见类型约束

课件列出的常用约束包括：

| TableGen 名称 | MLIR 中的典型类型 | 直观含义 |
|---|---|---|
| `I1`、`I8`、`I32`、`I64` | `i1`、`i8`、`i32`、`i64` | 指定宽度的整数 |
| `AnyInteger` | 任意整数类型 | 不限制具体位宽 |
| `AnyType` | 任意类型 | 不限制类型 |
| `AnyTypeOf<[...]>` | 给定集合中的任意类型 | 从几个候选约束中选择 |
| 用户自定义类型 | 例如 `List_ListType` | 由 dialect 定义的类型 |
| `Optional<...>` | 可选项 | 该 operand 或属性可以不存在 |
| `Variadic<...>` | 可变数量项 | 允许 0 个或多个同类项 |

例如：

```tablegen
let arguments = (ins SignlessIntegerLike:$lhs,
                     SignlessIntegerLike:$rhs);
let results = (outs SignlessIntegerLike:$result);
```

这表示 `lhs`、`rhs` 和 `result` 都必须是无符号信息的整数类类型，常见例子包括 `i32` 或 `i64`。

### 4.2 `ANY` 是示例中的占位符

课件练习中出现了这样的类型：

```mlir
!list.list<ANY>
```

这里的 `ANY` 是练习材料中的占位写法，意思是“list 元素类型可以是任意类型”，不是一个需要照抄到所有真实代码中的具体 MLIR 类型名。

## 6. generic syntax：最通用、但比较冗长的写法

### 6.1 `list.range` 的 generic syntax

前面的写法使用了 MLIR 的通用语法：

```mlir
%2 = "list.range"(%lb, %ub)
     : (i32, i32) -> !list.list<ANY>
```

generic syntax 明确写出：

- Operation 的完整名字；
- 所有 operands；
- 所有 operand 类型；
- 所有 result 类型。

它的优点是规则统一、信息完整，适合：

- 最初测试一个 Operation；
- 调试 parser 或 printer；
- 描述复杂或暂时没有 custom syntax 的 Operation；
- 避免因为自定义语法写错而无法验证 Operation 结构。

缺点是比较冗长，而且有些信息是重复的。课件希望把它改写成：

```mlir
%2 = list.range %lb to %ub : !list.list<ANY>
```

这个写法保留了有意义的 `to`，去掉了不必要的括号和重复类型。

## 7. 用 `assemblyFormat` 声明文本语法

### 7.1 `list.range` 的声明式语法

可以在 ODS 中使用 `assemblyFormat` 描述 custom syntax：

```tablegen
def List_RangeOp : List_Op<"range"> {
  let arguments = (ins I32:$lower, I32:$upper);
  let results = (outs List_ListType:$result);

  let assemblyFormat = [{
    $lower `to` $upper attr-dict `:` type($result)
  }];
}
```

对应的文本形式是：

```mlir
%2 = list.range %lb to %ub : !list.list<ANY>
```

把 `assemblyFormat` 拆开看：

```text
$lower
  打印或解析名为 lower 的 operand

`to`
  文本中的固定字面量 to

$upper
  打印或解析名为 upper 的 operand

attr-dict
  Operation 的属性字典位置

`:
  文本中的冒号

type($result)
  打印或解析 result 的类型
```

反引号包围的是固定文本，`$name` 引用 ODS 中命名的 operand/result，`type($name)` 表示对应值的类型。

### 7.2 `assemblyFormat` 的基本要求

课件强调了几个规则：

1. 每个 operand 都必须在语法中出现；
2. 除了可以由其他信息唯一推导的类型外，需要使用 `type(...)` 表达类型；
3. `attr-dict` 总是需要在声明式格式中有一个位置。

例如，下面的定义声明了两个 operands：

```tablegen
let arguments = (ins I32:$lower, I32:$upper);
```

因此 `assemblyFormat` 至少需要让 `$lower` 和 `$upper` 出现在语法中。否则 parser 无法从文本中得到这两个 operand。

`attr-dict` 即使当前 Operation 没有自定义属性，也为属性字典保留了标准位置。这样以后增加属性时，语法仍然有统一的扩展点。

## 8. 类型推导：减少重复类型

### 8.1 `list.reverse` 的重复信息

如果 `list.reverse` 的输入和输出类型始终相同，generic syntax 可能写成：

```mlir
%3 = "list.reverse"(%0)
     : (!list.list<ANY>) -> !list.list<ANY>
```

输入类型和输出类型重复写了一遍。我们希望使用：

```mlir
%3 = list.reverse %0 : !list.list<ANY>
```

### 8.2 使用 `AllTypesMatch`

ODS 可以使用 trait 表达输入和输出类型相同：

```tablegen
def List_ReverseOp
    : List_Op<"reverse", [AllTypesMatch<["input", "result"]>]> {
  let arguments = (ins List_ListType:$input);
  let results = (outs List_ListType:$result);

  let assemblyFormat =
      "$input attr-dict `:` qualified(type($input))";
}
```

这里的重点是：

```tablegen
[AllTypesMatch<["input", "result"]>]
```

它告诉 MLIR：

```text
input 和 result 的类型必须相同
```

因此 assembly format 只需要打印一次类型，另一侧可以根据 trait 推导出来。

`qualified(type($input))` 表示使用该输入的完整、明确的类型形式。对于自定义类型或可能存在名字冲突的场景，qualified type 能减少解析歧义。

### 8.3 类型约束和类型关系不是一回事

下面两件事需要区分：

```text
List_ListType
  说明“这个值必须是某种 list 类型”

AllTypesMatch<["input", "result"]>
  说明“两个值的类型还必须彼此相同”
```

前者约束单个值，后者表达多个命名值之间的关系。更复杂的关系可能还需要额外的 trait、predicate 或 C++ verifier。

## 9. Operation 文本语法的常见约定

课件建议遵循下面的形式：

```text
<arguments> attr-dict : <types>
```

例如 `list.push_back` 可以写成：

```mlir
%lo = list.push_back %li, %item
      : !list.list<i32>, i32 -> !list.list<i32>
```

不推荐把每个 operand 的类型拆散到不同位置：

```mlir
// 不推荐
%lo = list.push_back %li : !list.list<i32>, %item : i32
      -> !list.list<i32>
```

类型部分通常使用：

```text
operand types -> result types
```

如果 operand 类型或 result 类型不存在，或者能够由其他信息唯一推导出来，`->` 也可以省略。例如，只有一个输入、输出类型能够推导的 Operation 不需要重复打印所有类型。

统一的语法约定有两个好处：

- 初学者更容易阅读不同 dialect 的 Operation；
- parser、printer 和测试文件更容易保持一致。

课件还给出了 stretch goal，要求为下面三个 Operation 设计语法：

```mlir
%1 = "list.peek_front"(%0)
     : (!list.list<ANY>) -> ANY

%2 = "list.pop_front"(%0)
     : (!list.list<ANY>) -> !list.list<ANY>

%3 = "list.push_front"(%item, %0)
     : (ANY, !list.list<ANY>) -> !list.list<ANY>
```

其中：

## 11. Region：Operation 内部的代码区域

### 11.1 在 ODS 中声明 Region

有些 Operation 不只是输入、输出和属性，还会包含嵌套代码。例如：

- 函数包含函数体；
- 循环包含循环体；
- 条件 Operation 包含 then/else 区域；
- `list.map` 包含“如何处理每个元素”的函数体。

`Op` 基类中 Region 字段的默认形式可以理解为：

```tablegen
dag regions = (region);
```

具体 Operation 可以覆盖这个字段，声明它包含哪些 Region 以及 Region 的结构约束。

### 11.2 Region 约束

课件列出了几种常见的 Region 约束：

| 约束 | 含义 |
|---|---|
| `AnyRegion` | 不限制 Region 的基本结构 |
| `SizedRegion<N>` | Region 必须恰好包含 `N` 个 Block |
| `MinSizedRegion<N>` | Region 至少包含 `N` 个 Block |

例如，一个 Operation 可能要求它的 body 只有一个 Block；另一个 Operation 可能允许多个 Block 来表达分支控制流。

### 11.3 Region、Block 和 Operation 的关系

可以把层次关系画成：

```text
Operation
  -> Region
      -> Block
          -> Operation
```

Region 是 Operation 内部的代码区域容器，Block 是其中的一段顺序代码，Block 再包含具体 Operation。

这和前一讲介绍的 MLIR 结构一致，但本讲关注的是：如何在 ODS 中声明这些结构，以及如何给结构增加约束。

## 12. 与 Region 配合使用的常见 Trait

Trait 可以为 Operation 增加可复用的结构或语义约束。课件重点介绍了以下几种。

### 12.1 `SingleBlockImplicitTerminator`

```tablegen
SingleBlockImplicitTerminator<"CppOpClassName">
```

它用于要求 Region 具有单个 Block，并指定该 Block 使用哪一种 Operation 作为 terminator。适合循环体、条件体等结构简单、尾部操作固定的 Region。

### 12.2 `Terminator`

```tablegen
Terminator
```

这个 trait 标记某个 Operation 是 terminator。terminator 通常结束一个 Block，并把控制流转移到下一个位置、返回结果或把值交还给外层 Operation。

### 12.3 `HasParent` 和 `ParentOneOf`

```tablegen
HasParent<"CppOpClassName">
ParentOneOf<["CppOpClassNameA", "CppOpClassNameB"]>
```

它们约束一个 Operation 的直接父 Operation：

- `HasParent` 要求唯一的父 Operation；
- `ParentOneOf` 允许父 Operation 来自一个候选集合。

课件给出的 `scf.yield` 示例是：

```tablegen
def SCF_YieldOp : SCF_Op<"yield", [
  Terminator,
  ParentOneOf<["ForOp", "IfOp", "WhileOp"]>,
]> {
  // ...
}
```

这表示：

- `scf.yield` 是 terminator；
- 它只能出现在 `ForOp`、`IfOp` 或 `WhileOp` 的 Region 中；
- 它不是可以随意放在任意 Block 末尾的普通 Operation。

## 13. 第三个练习：实现 `MapOp` 和 `YieldOp`

课件要求实现一个 `MapOp`，对 list 中的每个元素执行 Region 中的代码：

```mlir
func.func @map(%list: !list.list<i32>) -> !list.list<i64> {
  %mapped = list.map %list -> !list.list<i64> with {
  ^bb0(%elem : i32):
    %ext = arith.extsi %elem : i32 to i64
    list.yield %ext : i64
  }
  return %mapped : !list.list<i64>
}
```

这个例子可以分成四层理解：

```text
func.func
  包含一个函数体 Region

list.map
  接收一个 i32 list，并声明返回一个 i64 list

^bb0(%elem : i32)
  MapOp 的 Region 中有一个 Block，Block 接收当前元素

list.yield %ext : i64
  每次处理一个元素时，Region 返回一个 i64 元素
```

`list.map` 的输入和输出元素类型可以不同：输入元素是 `i32`，输出元素是 `i64`。Region 的 Block 参数应当与输入 list 的元素类型匹配，而 `list.yield` 的值应当与输出 list 的元素类型匹配。

课件特别指出，花括号 `{ ... }` 中的内容就是 Region 的语法，对应 `assemblyFormat` 中的 `$region`。

## 14. 为什么不是所有结构都能只用 TableGen 表达

ODS 很适合描述规则、局部、可声明的结构约束，但有些约束涉及多个对象之间的动态关系。

考虑下面这个错误例子：

```mlir
func.func @map(%list: !list.list<i32>) -> !list.list<i64> {
  %mapped = list.map %list -> !list.list<i64> with {
  ^bb0(%elem : i16):
    // ...
  }
  return %mapped : !list.list<i64>
}
```

这里输入 list 的元素类型是 `i32`，但 MapOp body 的 Block 参数却是 `i16`。Operation 的字段数量可能都正确，Region 也可能确实有一个 Block，但这个跨对象的类型关系不正确：

```text
body block argument type
    必须等于
input list element type
```

这种关系不一定能仅靠普通的字段声明表达，因此需要额外的 C++ verifier。

## 15. 在 C++ 中补充 verifier

### 15.1 声明需要 verifier

在 ODS 中可以为 Operation 开启 verifier：

```tablegen
def List_MapOp : List_Op<"map", [...]> {
  // ...

  // 在进入 Regions 之前验证
  let hasVerifier = 1;

  // 或者在进入 Regions 之后验证
  let hasRegionVerifier = 1;
}
```

课件区分了两类入口：

```text
LogicalResult MapOp::verify()
  验证 Operation 本身和进入 Region 前可以检查的内容

LogicalResult MapOp::verifyRegions()
  验证依赖 Region、Block 或 Region 内部结构的内容
```

具体选择哪一个，取决于检查逻辑是否需要访问 Region 内部。

### 15.2 verifier 的基本返回方式

一个 verifier 通常遵循下面的模式：

```cpp
LogicalResult MapOp::verify() {
  Block &body = getBodyBlock();

  if (body.getNumArguments() != 1)
    return emitOpError(
        "expects the body to have exactly one argument");

  Type inputElementType =
      getInput().getType().getElementType();

  if (body.getArgument(0).getType() != inputElementType)
    return emitOpError("expects the body argument type (")
           << body.getArgument(0).getType()
           << ") to match the element type of the operand list (")
           << inputElementType << ")";

  return success();
}
```

这段代码做了两件事：

1. 检查 body Block 是否恰好有一个参数；
2. 检查这个参数的类型是否等于输入 list 的元素类型。

几个常见 API 的作用是：

- `getBodyBlock()`：取得 MapOp 的 body Block；
- `getInput()`：取得输入 list operand；
- `getType()`：取得一个值的类型；
- `getElementType()`：取得 list 类型中的元素类型；
- `emitOpError(...)`：报告带有 Operation 上下文的诊断；
- `success()`：表示验证通过。

验证失败时，错误信息应尽可能说明“哪个关系不满足”，而不是只返回一个没有上下文的失败值。对初学者来说，好的诊断通常直接指出：

```text
实际类型是什么
期望类型是什么
哪个 operand、result、Block 参数或 Region 出错
```

### 15.3 ODS 和 C++ verifier 的边界

可以用下面的方式划分职责：

| 问题 | 更适合用什么表达 |
|---|---|
| Operation 属于哪个 dialect、叫什么 | ODS |
| 有几个 operands/results | ODS |
| 单个值允许哪些类型 | ODS 类型约束 |
| 两个值类型相同 | trait，例如 `AllTypesMatch` |
| Region 有几个 Block | Region constraint |
| terminator 是什么 | trait |
| body 参数必须等于输入元素类型 | C++ verifier 或更强的 predicate |
| 需要遍历 Region 才能判断的复杂关系 | C++ verifier |
| 声明式格式无法表达的特殊文本语法 | C++ custom parser/printer |

ODS 不是为了替代所有 C++。它的目标是自动生成常规、重复、结构化的部分，把开发者的精力留给真正有领域意义的语义。

## 16. 自定义语法：`assemblyFormat` 不够时怎么办

课件最后两页分别以 **Defining custom Syntax in C++** 和 **Pretty MapOp** 为主题，说明了另一种情况：

```text
简单、规则的文本语法
  -> 使用 ODS 的 assemblyFormat

特殊、复杂或需要精细控制的文本语法
  -> 在 C++ 中实现 custom parser/printer
```

如果声明式 `assemblyFormat` 无法表达想要的语法，可以为 Operation 开启 C++ 自定义汇编格式，并实现解析和打印逻辑。典型结构可以概括为：

```tablegen
def List_MapOp : List_Op<"map", [...]> {
  // ...
  let hasCustomAssemblyFormat = 1;
}
```

然后在 C++ 中实现类似下面的接口：

```cpp
ParseResult MapOp::parse(OpAsmParser &parser,
                         OperationState &result) {
  // 读取自定义的 map 语法，填充 result
}

void MapOp::print(OpAsmPrinter &printer) {
  // 按希望的漂亮格式打印 MapOp
}
```

这类 C++ 代码需要自己负责更多细节，例如：

- operand 的解析顺序；
- 类型和属性的解析；
- Region 的解析；
- 语法错误的诊断；
- 打印结果是否能再次被 parser 读回。

因此，实践中通常遵循这个优先级：

1. 先使用 generic syntax 验证 Operation 结构；
2. 如果只是格式更简洁，优先用 `assemblyFormat`；
3. 只有声明式格式确实不够时，才写 C++ custom parser/printer。

“Pretty MapOp”练习的重点不是让代码看起来更复杂，而是让打印出来的 MapOp 更符合这个 dialect 的领域语法，同时保持 parse/print round trip 正确。

## 17. 一个完整的 ODS 工作流程

从一个新 Operation 的想法到可测试的实现，通常可以按下面的顺序进行：

```text
1. 先确定 Operation 的语义
   输入是什么，输出是什么，是否有 Region

2. 在 .td 文件中声明基本结构
   dialect、mnemonic、arguments、results、regions

3. 添加类型约束
   I32、AnyType、用户自定义类型、Variadic 等

4. 添加可复用 trait
   AllTypesMatch、Terminator、HasParent 等

5. 先使用 generic syntax 写 round-trip 测试
   确认结构和类型约束正确

6. 用 assemblyFormat 设计可读语法
   尽量减少重复类型，遵循统一约定

7. 编译并运行测试
   检查生成代码、解析和打印

8. 为 ODS 无法表达的关系补充 C++ verifier

9. 如果声明式语法仍然不够，再实现 C++ parser/printer
```

这个顺序的价值在于：先验证 Operation 的结构，再优化文本外观，最后处理特殊语义。这样更容易定位问题属于哪一层。

## 18. 初学者容易混淆的几个概念

### 18.1 `class` 和 `def` 的区别

```text
class = 定义可复用的描述模板
def   = 创建一个具体的、可被生成器处理的 Operation 定义
```

不要把 TableGen 的 `class` 直接理解成运行时 C++ 对象。

### 18.2 mnemonic 和 C++ 类名的区别

```text
list.reverse
  是 MLIR 文本中的 Operation 名字

ReverseOp
  是生成的 C++ Operation 类名
```

两者相关，但不是同一个命名空间或命名规则。

### 18.3 generic syntax 和 custom syntax 的区别

```mlir
// generic syntax
%r = "list.reverse"(%input)
     : (!list.list<i32>) -> !list.list<i32>

// 使用 assemblyFormat 的 custom syntax
%r = list.reverse %input : !list.list<i32>
```

generic syntax 更通用、更冗长；custom syntax 更贴近领域、更易读，但需要额外声明或实现。

### 18.4 类型约束和 verifier 的区别

类型约束适合描述：

```text
“这个 operand 必须是 i32”
“这个 result 必须是 ListType”
```

verifier 适合描述：

```text
“这个 Block 参数必须等于另一个 operand 内部的元素类型”
“这个 Region 内的 yield 数量必须和结果结构匹配”
```

前者通常是局部声明，后者经常需要读取多个字段、遍历 Region 或执行条件判断。

## 19. 本讲总结

### 19.1 ODS 解决什么问题

ODS 用声明式方式描述 MLIR Operation，并自动生成大量常规 C++ 代码，减少以下工作：

- Operation 的字段访问器；
- operands 和 results 的基础声明；
- 类型约束相关代码；
- 常规 parser/printer 支持；
- 部分 builder、verifier 和 trait 注册代码；
- 与 Operation 定义相关的重复样板。

### 19.2 TableGen 需要记住什么

```text
class
  可复用的描述模板

def
  具体的定义，生成器主要处理它

let
  设置或覆盖字段

dag
  描述带有操作符、顺序和命名元素的结构
```

### 19.3 定义 Operation 需要描述什么

至少要考虑：

```text
所属 dialect
Operation mnemonic
operands
results
类型约束
traits
regions
terminator
assemblyFormat
verifier
```

### 19.4 最值得记住的三句话

1. **ODS 的目标不是让 Operation 自动拥有所有语义，而是自动生成规则、重复、结构化的代码。**
2. **`assemblyFormat` 适合表达常规文本语法；复杂的跨字段语义和特殊 parser/printer 仍然需要 C++。**
3. **一个健壮的 MLIR Operation 通常由 ODS 声明结构，由 traits 复用通用约束，再由 verifier 补足无法声明式表达的关系。**
